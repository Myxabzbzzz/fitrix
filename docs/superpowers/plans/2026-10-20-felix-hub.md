# Wave 2B: Felix Hub — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The Felix tab opens a hub with 9 topics (Gym, Fitness, Running, Cycling, Football, Winter sports, Nutrition, Recovery, App assistant) and recent chats. Each topic chat knows the user's data for that topic (today's plan, check-in, last workout, food today) and offers topic questions.

**Architecture:** `AssistantTopic` becomes a fixed list of 9 ids (the 6 sports plus `nutrition`, `recovery`, `app`). Existing history keys stay as they are, so current chats survive. The Felix branch gets `/felix` (hub), `/felix/all` (all chats) and `/felix/chat/:topic` (chat). A per-topic `FelixSnapshot` is built from existing providers. The app sends it with each message as `context`; the backend sanitizes it into a prompt section. The `chat_messages.topic` check gets the two new topics (migration; cloud apply only after Муха's explicit «да»).

**Tech Stack:** Flutter 3, Riverpod 2, go_router, SharedPreferences; Node backend (`backend/`, `node --test`); Supabase Postgres + pgTAP.

**Spec:** Owner request 2026-10-19 «давай felix-хаб» → «начинай» (no questions; Claude designs from the clickable prototype `~/РАБОТА/fitrix-design/design/clickable/mock_felix.html`, screens «Felix hub», «Felix · Recovery», «All chats»). Decisions below are Claude's calls, listed in the handoff for Муха.

## Review Focus

- Messages from the new topics must not block chat sync of the other topics when the server rejects them (cloud without the migration yet): push is per topic, so one topic's failure does not stop the others. Test in Task 2.
